설계 원칙

  1. 데이터마다 원본(단일 작성자)을 하나로 정한다. 식권·거래·잔액은 기기가, 고객사·이용자는 서버가 원본이다. 한 데이터를 두 곳에서 고치지 않으므로 병합 충돌이 생기지 않는다.
  2. 서버가 죽어도 현장(스캔·차감)은 계속 동작한다. 기기는 마지막으로 받은 고객사·이용자로 동작한다.
  3. 거래 내역은 수정·삭제하지 않는다. 오류는 취소 거래를 추가해 바로잡는다. 잔액은 항상 거래 합계로 계산 가능해야 한다.
  4. 모든 업로드는 재전송해도 안전(멱등)하다. 레코드마다 기기가 만든 UUID를 가진다.
  5. 가맹점 데이터는 서버에서 철저히 격리한다.

3. 데이터 소유권

데이터원본방향비고
식권, 거래 내역(잔액)기기기기 → 서버 (push)서버는 열람용 사본. 서버에서 수정하지 않는다.
고객사, 이용자서버서버 → 기기 (pull)서버에서 등록·수정(엑셀 일괄 등록 포함). 기기는 읽기 전용이며 삭제는 비활성(soft delete)만 한다.
가맹점 계정, 기기 API 키, 관리자 계정서버서버 내부공급사 관리자가 등록·발급·폐기

기기 교체 시 복원서버 사본서버 → 새 기기식권·거래 전체 복원 API + pull(rev 0부터)
왜 이렇게 나누는가: 거래·잔액은 현장에서 실시간으로 바뀌므로 기기가 원본이어야 하고(서버가 끊겨도 동작), 고객사·이용자는 사무실에서 PC로 관리하는 데이터라 서버가 원본이어야 편하다. 데이터마다 작성자가 하나뿐이어서 양방향이지만 충돌 해결 규칙이 필요 없다.
단일 기기 = 단일 장애점. 기기를 분실하거나 브라우저 데이터가 지워지면 마지막 동기화 이후의 거래는 사라진다. 대응: ① 동기화 횟수를 늘리고 ② 마감 시점 자동 동기화를 두고 ③ navigator.storage.persist()를 요청하고 ④ 날마다 JSON 백업 내려받기를 제공한다.

5. 동기화 방식 (동기화 버튼: push → pull)

기기 쪽

  • 모든 변경은 IndexedDB의 outbox에 증가하는 seq와 함께 기록된다.
  • 동기화는 마지막으로 서버가 확인(ack)한 seq 이후만 보낸다.
  • 실행 시점: 동기화 버튼(push + pull). 보조로 앱을 열 때·하루 마감 시 push만 자동 실행할 수 있다. pull은 버튼을 눌렀을 때만 한다(영업 중 고객사·이용자 정보가 갑자기 바뀌지 않도록). 브라우저 백그라운드 동기화는 iOS에서 불안정하므로 의존하지 않는다.

요청 / 응답

POST /wp-json/couponman/v1/sync/push        Authorization: Bearer <기기 API 키>
{
  "batch_uuid": "…",              // 같은 배치를 재전송해도 한 번만 반영
  "seq_from": 1201, "seq_to": 1264,
  "clients": [...], "members": [...], "tickets": [...], "transactions": [...],
  "check": { "ticket_count": 310, "balance_sum": 18450000 }   // 기기 전체 합계
}
→ 200 { "ack_seq": 1264, "server_check": { "ticket_count": 310, "balance_sum": 18450000 } }
  • 서버는 merchant_id를 API 키에서 도출한다. 요청 본문의 merchant 값은 신뢰하지 않는다.
  • (merchant_id, uuid) 기준 UPSERT. 거래는 INSERT only(이미 있으면 무시).
  • 배치는 DB 트랜잭션으로 전부 반영하거나 전부 롤백한다. 한 번에 약 500건 이하로 나눠 PHP 실행 시간 제한을 피한다.
  • 응답의 server_check가 기기의 check와 다르면 화면에 경고하고 전체 재동기화를 제안한다.

서버 → 기기 (pull: 고객사·이용자)

GET /wp-json/couponman/v1/sync/pull?since_rev=340      Authorization: Bearer <기기 API 키>
→ 200 { "to_rev": 352,
        "clients": [ {uuid, name, …, status, rev}, … ],
        "members": [ {uuid, client_uuid, name, phone, …, status, rev}, … ],
        "has_more": false }
  • 서버는 rev > since_rev인 고객사·이용자만 내려준다. 기기는 받은 값으로 그대로 덮어쓰고(서버가 유일한 작성자) 마지막 to_rev를 저장한다. 많으면 has_more로 나눠 받는다.
  • 삭제는 status=비활성으로 전달되므로 기기에서도 사라지지 않고 상태만 바뀐다.
  • 기기의 고객사·이용자 화면에서는 등록·수정 메뉴를 제거하고 "서버에서 관리합니다. 동기화 버튼으로 최신 정보를 받으세요" 안내를 둔다.

동기화 버튼의 순서

  1. ① push — 거래·식권 변경분을 먼저 올린다(서버가 최신 잔액을 갖도록).
  2. ② pull — 서버에서 고객사·이용자 변경분을 받는다.
  3. ③ 합계 검증 — 기기와 서버의 식권 수·잔액 합계를 비교한다.
  4. ④ 결과 표시 — "올림 n건 / 받음 n건 / 경고"와 마지막 동기화 시각.
  • ①이 실패하면 ②는 하지 않고 재시도를 안내한다(부분 반영 방지). 오프라인이면 버튼을 막고 사유를 표시한다.
  • 마지막 pull이 24시간 이상 지났으면 기기 상단에 "서버 정보가 오래되었습니다" 배너를 표시한다.
  • pull로 받은 비활성 이용자의 식권은 스캔 시 거부하는 것을 기본 정책으로 한다(10장에서 확정 필요).

기기 복원 (새 기기로 교체)

  1. 공급사가 기존 기기 키를 폐기하고 새 키를 발급한다.
  2. 새 기기에서 GET /sync/restore로 해당 가맹점 전체 데이터를 내려받아 IndexedDB를 채운다.
  3. 이후 거래는 새 기기에서만 발생한다.

6. 보안

  • HTTPS 필수. 앱 파일도 같은 HTTPS 도메인에서 배포해야 PWA 설치와 QR 카메라가 동작한다.
  • 기기 API 키는 서버에 해시로 저장하고, 가맹점/기기 단위로 발급·폐기한다. 키는 발급 시 한 번만 표시한다.
  • 가맹점 격리: 모든 조회 쿼리는 로그인 사용자의 merchant_id(고객사 담당자는 추가로 client_id)를 서버 코드에서 강제한다. 요청 파라미터로 받지 않는다.
  • 역할: cm_provider_admin, cm_merchant_manager, cm_client_contact (WordPress 사용자 역할로 구현). 관리자 계정은 2단계 인증.
  • 개인정보(이름, 전화번호)는 필요한 최소 범위만 열람시키고, 고객사에는 자기 회사 직원만 보인다. 식권 코드는 열람 화면에서 일부 마스킹한다.
  • WordPress 플러그인은 최소한만 설치하고, 업로드 API에는 요청 크기·횟수 제한을 둔다.
  • 스캔 시 검증: 코드 형식·체크 값, 사업자번호 일치, 요일 마스크, 잔액 충분 여부.

공급사 관리자가맹점 등록·상태, 기기 키 발급/폐기, 가맹점별 마지막 동기화 시각, 전체 현황

모든 화면 상단에 "마지막 동기화: 날짜/시간(기기명)"을 표시해 데이터 최신성을 알린다. 편집 저장 시에는 "기기에는 다음 동기화 때 반영됩니다"를 안내하고, 기기가 마지막으로 pull 한 rev와 서버 rev의 차이(미반영 변경 건수)를 보여 준다. 기존 external_dashboard.html의 홈·통계·월별 리포트 화면을 읽기 전용으로 바꿔 재사용한다.

10. 위험과 미결 사항

미결

  • 비활성·삭제된 이용자의 기존 식권: 스캔을 거부하는 것(기본안)으로 확정할지, 잔액이 남은 경우 환불·이관 절차를 둘지.
  • 서버에서 식권 상태 변경(정지/해지)을 허용할지. 허용하면 식권도 서버→기기 pull 대상이 되어 소유권 규칙을 다시 정해야 한다. 현재는 허용하지 않음.
  • 가맹점 단가 설정을 기기와 서버 중 어디서 편집할지(현재 기기 임시 가정).
  • 고객사가 이용자를 직접 등록·수정할 수 있는지(현재는 가맹점 관리자만).
  • 고객사 담당자 계정을 만들어 고객사가 직접 열람하는가, 가맹점이 대신 전달하는가?
  • 식권 구매(결제) 기록을 시스템에서 관리하는가(입금 확인, 후불 청구서), 충전 거래만 기록하는가?
  • 카페24 상품 사양(PHP 버전, DB 용량, 실행 시간, 외부 호출, 백업)
